# 旧共享上传的额度归属修复

2026-11-09，N4-05 / RB-12、RB-15及FF-H17增量。主线37/53完成、剩16项；资源11/17完成、剩6块。这里交付可核验的旧共享上传归属修复，不能据此关闭N4-05或完整上传功能。

## 问题与行为

旧逻辑只接受与当前工作区所有者相同的上传预留。历史记录若计在协作者名下，上传列表会隐藏它；即使实际文件、进度、case绑定有效，所有者续传仍返回404。真实反例见 `tmp/upload-owner-api-8ib0dks5/owner-result.json`：先通过生产接口上传实际文件，再将隔离SQL中的计费用户改成协作者以构造旧记录；不是模拟模型或固定存储回复。

现在列表显示需要修复的记录及权限标记。继续写入错误归属的会话返回409和 `upload_owner_reconciliation_required`，明确说明需要项目所有者处理。新增 `POST /api/v1/cases/{case_id}/uploads/{upload_id}:reconcile-owner`，只允许当前项目所有者发起。

修复按当前所有者额度锁、旧计费用户额度锁、case控制锁串行，重新核对工作区归属、实际目录前缀、原存储绑定及上传ID/路径/大小/进度。新所有者必须容纳尚未物化的内容；额度检查通过前不释放旧预留。用户归属、剩余字节和唯一的 `files.upload_owner_reconciled` 审计事件在同一个SQL提交中保存，固定事件ID使重试幂等。

该入口不创建远端写入池，不改上传文件、不搬迁内容、不替换case前缀。旧账户有活动写入池、当前case的未结算写入，或上传有活动分块转移时拒绝修复；不按TTL释放，也不假设活跃或未知写者已停止。旧记录及审计不删除。已结算且剩余为0的记录保留原结算状态。

## 用户界面

文件面板提供“检查旧上传”，展示路径、账面剩余额度和修复后的计费影响。所有者可选择“由项目所有者核算”；协作者看到联系所有者的说明，不能发起这项操作。绑定不一致的记录保留说明，不展示可执行的修复按钮。

提交期间禁止重复操作；失败保留记录和错误说明；成功提示与重新读取列表分别处理。网络中断后可检查状态再重试，不自动覆盖文件或恢复未知写者。界面沿用现有面板样式，调整标题和按钮组换行，长文件名保留可读内容。

本次按 impeccable 的 scoped hardening 流程查看原界面、检查最终渲染并运行机械检查，检测结果 `tmp/upload-owner-design-detector-final.json` 为 `[]`。生产构建通过，日志位于 `tmp/upload-owner-ui-azr8_wbr/production-build.log`；既有大包警告保留。PowerShell最初拒绝执行npm.ps1后改用npm.cmd，没有修改执行策略。

## 失败与清理

首次6组FS后端通过记录 `tmp/upload-owner-api-77rxuumb/owner-result.json` 作为早期证据保留，不重复计入最终36组。后端生产逻辑没有借浏览器失败放宽约束。

7份浏览器失败原样保留：FS的鼠标模式焦点断言、错误的夹具重置；S3的后台占用与提交观察、零额度时占用优先返回409、停靠布局重排时焦点位置、成功提示早于列表刷新、创建请求被拒绝后夹具误用undefined上传ID。最后一项导致的是测试seed接口500。最终脚本明确验证所有准备步骤的响应，读取实际提交屏障并等待列表刷新。文件树SQLITE_BUSY和运行环境探针通道关闭也出现在含提交暂停的联调日志中，原因尚未定位，不能据后续成功称为修复或自然场景已复现；继续原N4/N7范围。

日志检查曾误输出本轮隔离测试的WebSocket会话令牌；随后只读脱敏摘录。两个临时API和Vite现已退出，对应临时服务不再接受这些令牌。该事件不涉及模型密钥，不更改开发登录或凭据；原私有测试日志不进入源码包。

两个临时PostgreSQL数据库已删除；三个自建SeaweedFS服务均已停止。最终后端12个API出生身份、两个浏览器API/Vite均退出；另核对UI隔离库104条原生记录中的64个已观察Windows出生身份全部退出，见 `tmp/upload-owner-UI-process-exit-20261109.json`。数据库仍可能保留旧active阶段，不伪造其持久停止证明；未登记的出生窗口仍不能据此称为覆盖。
