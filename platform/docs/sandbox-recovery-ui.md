# 沙箱恢复界面与真实浏览器验收

2026-11-07。属于 N4-05 / FF-F58、FF-J16 的增量交付；全部53项主线及295项全功能目标继续有效。

## 已实现的操作

在终端点击“恢复文件”，选择当前算例的隔离沙箱会话。界面调用实际恢复核验接口；存活、身份未知或记录变化时不允许生成快照。原会话已退出时可创建快照，后端仍在执行前重新检查授权、进程及来源。

对话框区分正在生成、可下载、生成失败和执行中断。正在生成时禁止当前按钮重复提交；关闭界面不会主动取消已发出的 POST，也不会自动重发。重新打开后读取持久记录：有活动记录时每5秒刷新，否则每15秒观察，以覆盖 POST 尚未入库便重新打开的时间窗口。后台刷新保留已经加载的旧记录；手动刷新重新获取首页。创建请求断线时提示结果未知、先查看记录。

文件清单每页20条，显示文件大小、权限和空目录。下载前读取完成回执，接收长度不超过回执和136MiB上限，浏览器核对实际完整ZIP的SHA-256后才交给下载管理器；后端也独立核验归档。只允许一个当前界面的下载，卸载时取消读取。ZIP仍在浏览器内存中组装和计算哈希，尚未实现写入磁盘的低内存下载。

界面采用原生对话框：初始焦点在标题，Tab/Shift+Tab在控件间循环，Escape或关闭按钮返回入口。终端不再因为查看恢复信息被压缩到零高度。窄屏可纵向滚动，按钮至少44px，颜色复用项目语义变量。终端连接断开文案明确状态待核验，不能把断开一律描述为仍在后台运行。

## 本批证据

证据目录：`tmp/sandbox-recovery-ui-p4vulltp`。汇总及源码绑定：`tmp/mainline-sandbox-recovery-ui-evidence/validation.json`。

- `fixture-checks.json`：实际隔离API/SQLite/文件存储与生产前端构建；真实WSL沙箱写随机内容、0600文件、空目录、26个分页文件和长文件名；杀死并重启API；保留另一个真实存活沙箱；修改隔离镜像UUID回执制造真实恢复失败。6条环境准备检查中5条实际基础设施、1条故障注入。
- `browser-checks.json`：30条浏览器断言，28条实际交互/基础设施、2条真实归档损坏检查。存活拒绝、实际失败记录不可下载、生成禁用、关闭重开不重发、自动出现完成记录、3页清单、真实下载、服务重启后查询/下载、不同算例空记录均验证。
- `download-verification.json`：ZIP实际文件逐项匹配清单，随机内容一致，空目录及0600权限保留，长度和SHA-256与持久回执相符。
- `restart-download-verification.json`：实际API重启后再次下载，两个ZIP字节完全相同。
- 375×812、812×375和1280×900的深浅色截图；全部控件聚焦后可见，无恢复内容横向溢出，双倍文字不横向溢出。以减少动态效果偏好运行；本界面没有添加动画。截图已人工查看。
- `cleanup.json`：56个唯一原进程身份中55个直接观察为exited，1个Windows PID已被复用，当前创建时间晚于原始身份，证实原身份不存在。记录保留mismatch原始结果，不伪装为exited，也不停止复用PID的新进程。测试API/前端端口已关闭。

本批真实LLM调用0、模拟LLM调用0，未运行历史模拟回归。构建通过；范围内静态检查无错误，8条警告（原终端5条，新异步加载组件3条set-state-in-effect提示）。现有大体积前端bundle警告仍在。

验收不是一次全绿：最初发现反向Tab焦点移出、关闭重开后记录不自动更新，修改产品代码后重新通过。另有一次测试空目录名称写反，按实际创建路径修正；相关失败报告均保留。存活会话核验曾遇真实并发记录变化，界面拒绝创建，手动重新核验后确认存活。

原环境脚本最终清理等待只接受exited，遇到PID复用而超时，不能算原脚本整体通过。随后独立核验56个真实身份，并把只读核验器接回环境脚本；该核验器已实跑，集成后的完整环境启动过程没有重复运行。未修改生产进程身份不匹配时拒绝恢复的规则。

## 复验入口

1. 构建前端；审查 `server/sandbox_recovery_ui_fixture.py` 及导入辅助文件，通过 `tools/regression-llm-review.json` 登记后再运行环境脚本。
2. 从隔离目录ready.json取得公开测试信息；使用测试账户通过真实登录页进入算例、终端及恢复对话框。
3. Playwright设置 `page.recoveryFixture` 为ready.json内容，依次以 `page.recoveryStage` 选择 `create`、`download`、`layout`。执行 `tools/e2e-sandbox-recovery.mjs`，保存返回证据。
4. `server/sandbox_recovery_ui_verify.py <隔离目录> verify` 校验下载；`corrupt`和`restore`只修改经过隔离路径与真实回执检查的测试归档。两者之间运行浏览器 `corrupt` 阶段。
5. 写control.json的restart动作，确认restart-ack及实际服务存活后运行浏览器 `restart` 阶段。它还验证空算例；对照两次ZIP。
6. 写stop动作结束环境，核对实际清理结果。若观察超时，只核验已有身份，不能因此重启/重跑整个恢复任务。`sandbox_recovery_ui_cleanup.py`提供只读的独立身份核验。
