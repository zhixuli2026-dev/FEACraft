# 成果复制的持久存储预留

2026-11-06，N4-05 的一项增量。主线仍为 33/53 完成，剩余 20 项；本变更不单独关闭 N4-05。

发布成果原来在脱离数据库事务后复制文件，只能在执行目录监测中发现增长，不能提前把复制所需空间从用户余额中扣留。现在正常发布和 prebundle 恢复先取得持久预留，再写复制意图和成果；复制本身仍在数据库事务之外完成。

## 预留与实际用量

`PublicationStorageReservation` 与上传预留使用同一个用户额度锁，并共同计入 `storage_bytes_reserved`。归属使用案例所在工作区的所有者，绑定案例、存储后端及位置、发布 ID、清单摘要。额度不依赖 API 进程的内存状态，也不按 TTL 自动释放。

预估量包括一份输出文件、成果清单、复制意图、完成回执，以及文件存储的一个锁字节。临时意图和回执通过重命名安装，计入写入峰值；中断的旧副本作为实际占用另外计量。S3 使用不可变条件创建，已存在对象不能被一次重试重复覆盖为新版本。已保留的历史版本仍由实际用量扫描计费。

复制过程中保留整个预估量，不随已写字节递减。因此对并发写入采取保守计费：已写部分可能暂时同时出现在实际占用和预留中。本地普通错误只有在复制线程确实结束后才能释放未来写入额度；已经留下的文件不会因此免计费或被删除。S3 写入结果不确定时继续保留整个预留，客户端线程或进程退出不能证明远端请求停止。

## 进程退出和恢复

每笔活动预留绑定写入进程的宿主身份、PID 和出生标识，以及本次调用的随机 token。两个恢复进程不能同时使用一份未完成的预留。旧写入进程仍存活、出生身份不匹配、宿主不明或无法核验时拒绝接手；仅确认其真实退出后才允许重新准入。

恢复重新检查当前实际占用和现有预留，包括上一次复制遗留的文件。有效成果清单还不够，必须同时验证完整文件和相同摘要的 `ready.json`，才能认定无需继续分配空间。这样既不会把“文件齐全但回执缺失”误当作完成，也允许已完成复制在额度后来收紧时完成数据库结算。

`active` 保留全部未来额度，`materialized` 表示复制完成，`released` 表示本次写入已结束且未来额度释放；后两者剩余额度均为零。活动写入的成功/本地普通失败结算不持有案例锁，允许等待用户额度锁。文件存储恢复失败时，确认退出的写入者预留与发布失败状态在同一事务中结算，避免先提交失败、后释放额度之间再次崩溃的窗口。

后续归档额度核对进一步修正了 S3 结果不确定的情况：失败发布保留预留，启动扫描包含仍有预留的终态发布。只有完整成果和完成回执共同验证通过，才按实际物化结算；条件创建使后到请求不能重复分配已存在的同名不可变对象。此核验不发布成果，也不把任务改成成功。详见[输出归档与节点空间](output-archive-node-storage.md)。

额度不足会记录 `resource_limit`，明细为 `storage_limit / publication`，不能把原生命令成功退出误报成成果发布成功。无法核验存储或身份时保留证据，不把未知用量当成零。任何预留都不授予发布权限；原有案例、尝试、输入、发布头和恢复证据检查继续决定最终结果。
