# 工作流恢复与检查点续接：实现与待验收范围

2026-11-11更新：`resume-plan`、`:resume`和v5恢复图已实现。原封存输入重试通过SQLite/临时PostgreSQL实际CadQuery验收；工作流级串行OpenFOAM检查点已在FS/S3×SQLite/PostgreSQL四组合完成0.005、0.01两次实际续接、0.5最终场与fresh数值对照，差值均为0，S3缺失本机结果缓存和显式D确认亦通过。MPI/UDF等专业模式和其他原范围继续，不能把串行结果扩大为全部处理器。具体实现、失败和后续范围见[原子恢复记录](workflow-resume-atomic.md)。

## API与语义

已增加`GET /workflow-runs/{id}/resume-plan`，由服务端列出有可信原尝试的可恢复步骤、原尝试版本、可选方式及阻碍。读取不创建Job/流程，不控制未知执行者。未知/缺失封存、旧任意argv、未核验停止及不受支持的检查点必须明确拒绝，不能回退到从头运行。

已增加`POST /workflow-runs/{id}:resume`，固定外部幂等键，明确原流程/步骤/尝试和版本、case修订、用户确认及恢复方式。`retry_step`表示以原封存输入重试原步骤；`checkpoint`必须明确受支持求解器的真实写出时刻。两者不能混称，仍待原生支持的处理器不得虚报checkpoint可用。

原流程终态不重开，不修改旧Job、步骤、尝试或停止证明。新流程和新尝试持久关联原来源，响应明确实际恢复方式；同账户/case/键/请求读回同一新流程，不同请求拒绝，已存在回执也先重新授权。源尝试不再是请求族末次、来源变更或已有活跃流程时拒绝并说明原关联。

## 实现门禁

1. **图、阶段和来源。** 新图由注册处理器重建；起点通过真实现有工程证据校验。完成前缀不重复执行，后续B/C/D/E确认仍由原阶段接口负责。失败回退到V等情况必须明确用户恢复所需阶段，不能由resume默许审批。UDF等前置节点需核验原产物，不能按名字推断复用。
2. **真实恢复。** 复用`job_repeat.trusted/drained`、正式处理器及`solve_resume_handler`等原协议；checkpoint读取真实原结果、场、网格、时刻与工具链。输入失效要求显式重算，不能把当前目录补成原封存。多次续接保留同根及直接来源，普通重算不能带入旧checkpoint。
3. **一次事务后交付。** Run、Steps、新Job/attempt、输入、发布预留、来源审计及交付意图须在原子边界内一致持久化，之后才放行执行。`job_repeat.perform`使用的`case_write_capacity.committing`拥有整次提交，不能先调用该API边界再补工作流step_id；Redis worker可能在补关联前接走Job。应组合底层校验/分配能力，在关联完整后提交交付意图。
4. **锁、额度和中断。** 昂贵原生检查点/归档读取采用现有快照、锁外准备及锁内复核模式，复核权限、来源和文件/发布读集。新尝试引用旧请求族时，旧head的CAS和新head归属分别验证，不能把预分配前head摘要当永久不变证明。保留原预算，不隐式提高期限或额度；准备取消时实际收尾并保留未知占用。
5. **计划绑定。** 新恢复图有显式schema和可核验lineage，接入`locked_run`、详情、派发、事件、恢复上下文及重算；不能仅把新Job挂在步骤名下。普通重算从恢复流程开始时仍回到正式当前输入处理器。

## 验收范围与剩余

- SQLite/临时PostgreSQL：版本/账户/case/幂等冲突、来源与head变化、同请求并发、取消/交付中断、未知停止和旧无证明记录的拒绝。
- 已有真实注册CadQuery重试及四组合串行OpenFOAM真实checkpoint，从实际写出时刻继续并与fresh最终场比较；新旧关联、正式发布、原预算和后续显式D确认有实际证据。MPI/UDF等原有专业目标仍须核对，不以单处理器结果扩大范围。
- S3原结果缓存移走后从完整远端归档续接已通过；发现并修复取消任务不能上传完整归档的准入缺陷。其余跨环境、权限、交付/提交中断按原矩阵继续。
- Agent/模型回合若纳入验收，只调用已授权真实服务，记录实际模型、状态和证据；本页无模型调用。

这是完整范围的实施门禁，后续继续实现和验证。完整版本UI、阶段整合和全局刷新仍由原N6-04～07承接，并保留全部53/295目标。
