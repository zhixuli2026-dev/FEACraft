# 数据库提交前的产物恢复

本批推进 N5-04：注册处理器已经完成原生执行、专业产物校验、不可变包准备和所有写入排空，但 publication/head/Job 终态事务尚未提交。它与[已提交产物恢复](publication-alias-recovery.md)覆盖提交前后的两个窗口；N5-04、N2-06仍不据此关闭。

后续扩展已支持[产物复制中断恢复](bundle-preparation-recovery.md)：原生校验完成但尚未写入v1排空检查点时，可依据复制前持久证明补全bundle，写入独立v3恢复检查点，再进入本文流程。v3还须核对原准备事件和恢复复制排空事件；没有完整证明的更早阶段仍不重放。

原 owner 在 `record_drained` 之后保存 `finalization_intent`，记录成功退出、不可变包哈希，以及输入、输出、发布预留和排空检查点的哈希。同一事务写入 `attempt.finalization_prepared`，并更新本地准备对象的输出快照。若准备身份已经改变，不签发恢复证明，继续原来的失败判定。没有完整检查点、不成功或缺失完整产物的尝试不会获得成功恢复意图。

新 API 启动后将候选放入本实例的后台恢复任务，API 就绪不等待原生工具、大文件核验或过期占用。任务先只读检查执行 lineage、未取消状态、原始检查点、原生及所有子执行停止证明，并核对“写入已排空→准备意图”的持久事件顺序。原 worker 的精确出生身份必须已退出；活着、异机或无法确认的 owner 都不能被接管。

恢复只读取已有 journal 和 bundle，使用数据库保存的哈希重新构造准备证明。它不调用原来的 `prepare_for_finish`，不执行编译、求解、同步或专业 artifacts 重建。随后重新取得可续租的来源校验占用、校验不可变输入和产物、读取当前来源及依赖，进入原 `_finish_owned` 事务。该事务先复验完整恢复快照和历史，再原子提交发布指针、Job/attempt、工作流状态和 outbox。旧来源已变更时按原协议失败；已有产物保留供诊断。

两个 API 可以同时发现同一候选，但来源校验占用与最终 case 控制锁共同串行化提交。已被另一恢复任务提交、被取消、lineage改变或证明变化的尝试不能重复提交。恢复审计 `attempt.finalization_recovered` 与终态同事务；不创建新 Job、attempt 或发布代次。后续兼容文件写入使用同一哈希计划，数据库已经提交而回执丢失则转入已提交产物恢复路径。

后台任务在关闭 API 时被取消并等待清理，文件线程先排空再释放占用。原 owner 遗留的占用须按既有协议过期并独立提交撤销；不会因原 owner 已退出而撤销另一个恢复实例刚取得的占用。后台任务状态仅用于本机排重，不能作为跨实例执行权。当前触发点仍是启动对账，不宣称完整跨主机自动故障接管。

验证使用真实 Pandoc 报告及文档合成：准备后中断、来源占用已取得后中断、两个 API 同时恢复、离线来源编辑、损坏 bundle、原 owner 仍活、重复启动。检查原 Job/attempt/产物身份、bundle 字节及修改时间、终态事件只出现一次，并在恢复进程禁止调用原生准备入口。另保留已有取消、准备绑定改变、发布身份改变与最终 commit 失败的原始断言。
