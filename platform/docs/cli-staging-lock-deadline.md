# CLI 的 S3 准备锁范围与下载期限

2026-11-07，接续 [CLI 启动共享期限](cli-startup-shared-deadline.md)。原实现持有 case 写锁下载整个 S3 副本；同步下载没有逐块检查请求期限，外层取消后仍可能继续读完全部文件。本次将批量下载移出 SQL 事务，并在下载前后和每块读取边界检查继承的期限。

## 实现

会话准备先在短事务内鉴权，记录来源前缀、权限模式、模型、会话 API 配置选择及 case 控制行的事件序号；提交事务后才创建节点空间预留、枚举和下载实际版本固定的对象。完整副本仍须通过原有第二次源目录核验。

下载结束后重新取得 case 写锁，重新鉴权和检查凭据，并比较上述绑定与事件序号；不一致则以 `input_stale` 拒绝启动，清理未被 CLI 使用的副本。最终 owner 的创建及提交仍在这次事务中。会话关闭时的修改回传继续使用原有受控同步协议。

事件序号检查采取保守策略：下载期间任何 case 事件都可能要求显式重新启动，包括与输入文件无关的事件。它阻止协作写入发生后继续使用旧副本，但不是对绕过平台锁和事件协议的外部写入提供新的原子快照保证。原有对象 ETag 条件读取和目录前后核验仍保留。

公共 `staging_download` 在枚举、清单编码、空间准入后、每个文件、GET 返回后、每次正文读取前后和清单写入前后检查当前请求截止时间。GET 已返回的实际响应体在超时路径上关闭；已开始的读取先实际返回，超时后不写入刚返回的块、不发起下一次读取。已经创建的随机暂存根及清单清理完成后才释放空间预留。线程返回完整副本时先捕获副本身份，再传播取消，避免丢失清理责任。

## 真实对象存储与 CLI 验收

入口：`platform/server/live_llm_cli_staging_acceptance.py --source-profile-id 26 [--postgres]`。使用独立 SeaweedFS 4.52、独立 bucket/节点目录、实际 S3 条件读写、实际数据库以及已安装的 Windows Codex。准备失败的用例没有启动 CLI；正常用例使用真实 stdio 初始化、关闭和出生身份退出核验。没有替换 CLI 初始化结果或推理回复。

SQLite 与 PostgreSQL 各九场景：

| 场景 | 通过条件 |
| --- | --- |
| 完成实际源目录枚举后到期 | 后续分配停止，未启动 CLI |
| 实际 GET 返回后到期 | 响应体关闭，正文 read 次数为 0 |
| 实际第一块读取后到期 | 响应体关闭，read 次数为 1，没有第二次读取 |
| 实际清单写入后到期 | 清单与暂存文件均清理完成 |
| 完整下载返回前到期 | 等待实际线程、捕获副本并清理，不创建 CLI owner |
| 完整下载后并发修改源文件 | 独立事务提交实际 S3 写入与文件变更事件；启动拒绝，保留新的源内容 |
| 完整下载后并发修改权限 | 独立事务修改会话权限；重新核验拒绝启动 |
| 完整下载返回前连续取消三次 | 外层仍等待线程；返回后清理副本，无节点预留遗留 |
| 普通准备、实际 CLI 启动和关闭 | 活动记录与真实初始化成立，关闭后暂存清理、进程实际退出 |

所有暂停场景都用独立数据库事务写同一 case 控制行，并要求 3 秒内完成，证明批量 I/O 不再持有该锁。最终两套矩阵均通过；所有异常用例没有 CLI 登记记录，所有暂存根、清单、清理标记及节点预留均已清理，源文件内容及大文件摘要符合预期。计时出现 0.0 是时钟精度限制，不宣称零延迟。
