后续状态：第十七批已完成四类交互入口的批量同步迁移，见[交互会话同步](interactive-staging-transfers.md)。下文保留第十六批的验收边界；元数据请求、补偿恢复及跨主机证明仍未关闭。

## 原因与实现

之前 `staging_sync.sync_job` 在一个算例 SQL 控制事务内完成文件收集、远端备份、内容上传及提交。作业心跳和取消也需要同一控制锁。把延迟注入真正的 `collect` 后，心跳停止推进，测试中的 10 秒租约过期；此前仅在调用同步之前暂停的夹具不能证明这个窗口安全。原始复现保存在 `tmp/staging-lock-before.json`，不应在修复后重复当作基线运行。

现在旧作业使用 `s3_staging_transactions`，按以下边界执行：

1. 短控制事务检查作业归属、收尾阶段、算例绑定，并处理上一笔待恢复的文件事务。
2. 关闭 SQL 会话后收集改动、流式准备不可变备份和新内容。这里不写算例正式文件。
3. 在算例协调事务内发布带写入进程身份的 pending 清单。清单与源绑定、文件摘要和预留 SQL 事件 ID 一起校验。
4. 提交控制事务后，逐文件执行现有条件写入/删除。每个文件开始前再次检查作业归属和取消状态；正在执行的不可取消 I/O 必须排空。
5. 再次检查作业与算例，短事务写入 SQL 提交证明、失效别名和文件变化事件。
6. 所有传输线程及 SQL 提交/回滚结束后，发布与本次清单精确绑定的 `drained.json`。

取消发生在文件传输期间时，取消请求可以先持久化，后续文件不会继续启动。同步失败、任务取消或未知提交均保留本地副本；后续恢复依照 SQL 证明决定保留新内容还是恢复旧内容。作业取消不会被晚到的同步成功改写。

普通文件保存和交互会话仍使用原有事务入口；共享实现只抽出了不修改正式文件的准备阶段。新同步先恢复上笔已提交的 pending，避免准备阶段将它误判为仍有竞争事务。

## 活跃写入者保护

恢复入口先检查清单及写入者状态，然后才读取整批备份。写入进程仍存活、主机不同、身份无法核验时返回 `file_sync_busy`，不能依据租约过期或缺少 SQL 事件直接回滚。

只有匹配的排空证明或操作系统确认原写入进程已退出，才进入原有内容/元数据/SQL 证明恢复流程。未知主机身份保持现场，不推断另一台机器的进程已经死亡。损坏的排空证明也不能授权恢复。发起同步的执行上下文只允许在自己的最后提交事务中绕过活跃写入者阻挡，不能跳过算例绑定和正常写入准入检查。

慢 I/O 夹具使用真实原生进程、独立数据库和受控文件系统 S3 替身；实际对象存储故障矩阵另用 SeaweedFS。延迟 12 秒时，10 秒作业租约仍由心跳推进。所测取消响应约 0.14～0.27 秒，这些是本机夹具观测，不是部署性能承诺。

旧夹具改用明确的直接运行器入口，避免公共入口的新隔离工作目录/类型化发布机制先行拒绝假 OpenFOAM 场文件。它检查历史收尾 I/O，不声称验证真实 CFD 求解或公共提交契约；公共入口由已有独立验收覆盖。第一次准备/写入延迟钩子误拦截测试建例时的普通文件保存，已限制到真实载荷启动之后。取消未同步的日志保留在副本，夹具不再要求远端已生成解析摘要。

## 仍需完成的边界

- 终端、可视化、Agent Shell、CLI 的旧交互同步仍在协调事务内执行批量 I/O，需要迁移并保留各自授权/会话收尾语义。
- 清单发布/读取等元数据请求仍在短 SQL 协调事务内；存储故障导致这些请求长时间阻塞的情形尚未解决，不能宣称所有同步 I/O 都不持锁。
- 已排空或已退出事务的批量校验、补偿恢复仍在恢复锁内。后续需处理该路径的长时锁占用，保持恢复互斥和提交证明。
- 排空证明发布失败时保守保留写入者保护；跨主机无法验证停止时不会自动解除。恢复操作入口与完整跨主机部署仍在原范围内。
- 准备清单发布前的残留、会话恢复、缺证明数据、已提交缓存重建、索引对账及原 UDF 409 等原有待办保留。
