# 根原生分配阶段的失联恢复

2026-11-16，N4-07 原失联恢复范围。沿用已有内核分配控制器的 `retire` / `abandon` 回执和 v4 检查点，不增加操作授权流程。

## 原问题与实现

普通受控 WSL 根在启动意图与 guardian 建立前先分配内核范围。原 worker 在分配中失联时，执行身份和启动观察都为空，原范围恢复依赖 guardian，无法完成收尾。

根分配意图现在同时保存执行许可顺序与相关实现摘要：业务执行必须在原启动登记后获得许可。新恢复仅接受这一明确约定及其支持的当前实现；历史空意图仍可供原正常范围恢复校验，但不能自动获得新的“业务从未释放”证明。专业 child 的原意图格式保持。

独立恢复者必须在同一宿主观察到原 worker 已退出，并逐一观察原记录中已知的分配宿主和 Linux 创建者退出。原分配确认已保存时，撤销原 inode 绑定范围；创建者准备已保存而分配确认缺失时，复用原创建者绑定的 abandon，核对真实已退出创建者，只移除未交付的空分配。若原准备也缺失，则保留未知引导进程列表和空撤销回执，不声称观察到了它们的退出。

原启动意图、guardian、业务入组或执行登记一旦存在，就拒绝这条分配阶段恢复，交由原执行范围恢复处理。锁内重新核对原任务快照、完整相关历史及取消时间，随后将同一 attempt 收尾为 interrupted 或 cancelled，结束失败发布预留，保留原公开成果。原身份、准备缺失、stop 和原事件均不补写，也不重放业务命令。

## 实际验收

`live_llm_allocation_loss_acceptance.py` 使用真实 PostgreSQL、S3、Redis、Windows API、Windows/Linux worker，覆盖：

1. 分配意图提交后失联。
2. 原创建者准备已提交、许可尚未返回时失联。
3. 实际分配控制器已返回结果，但 SQL 分配确认尚未写入时失联。
4. SQL 分配确认已提交、根启动意图尚未建立时失联。
5. 未确认分配失联后，通过实际 API 取消再恢复。
6. 上一轮“实际根已创建、首条观察缺失”的兼容路径。

故障钩子调用原生产函数，实际退出 worker（17），不会替换控制器、模型或发布结果。未确认分配的真实回执仅作为测试观察，不提供给生产恢复；生产只能读取原 SQL 准备和创建者记录。实际查看原分配 empty → absent，并核对 abandon 解析到的范围与原未确认分配一致。各场景新命令均按 UID65534 执行并发布随机文件，最后由真实 DeepSeek 文件工具读取。

Windows/Linux 分别校验凭据，模型调用与纯协议修改检查分开计数。没有模拟 LLM 回归。
