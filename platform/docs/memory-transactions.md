## 交付行为

正式 Agent `update_memory` 在算例锁下读取权威文件存储或 S3 对象，按既有规则追加/压缩到 64 KiB，再交给统一文件事务日志。读取绑定文件版本，派生内容携带旧文件 SHA-256 与长度；读完后被外部修改则拒绝覆盖。S3 不再通过同步工具辅助函数写本地缓存。

记忆文件的 SQL 提交证明与 Agent 工具结果由调用者一同提交。中断或回滚后，下一次协调读取恢复旧记忆；提交后进程退出则保留新记忆。完整工具自动执行和审批入口均在已知提交后整理日志。同步 `_tool_update_memory` 仅保留为独立工具兼容辅助，正式异步 Agent 入口使用 `write_memory`。

模型请求注入长期记忆前也获取算例锁并处理未完成事务；版本绑定读取完成后才生成上下文。存储冲突/损坏不再被解释成“暂无记忆”。缺失文件仍作为空记忆处理。并发追加读取前一个已提交版本，两条经验各保留一次；非法操作不改变文件。原追加 16 KiB、总记忆 64 KiB 和 UTF-8 遗忘规则保持。

本批同时修复回归发现的提交后回收站竞争：保存先提交，另一个请求随后删除算例时，日志整理不应再把成功保存误报为 `409 case_unavailable`。整理仍持有算例锁、核对证明；只允许这个已提交后的内部整理步骤读取已删除状态，不放宽普通保存和访问的可用性检查。删除方已在移动目录之前完成恢复，恢复算例后内容与提交时一致。

## 验证证据

规范目录：`tmp/mainline-N2-memory-transactions-evidence/`。

- SQLite 文件存储/S3 各 8 组分批验证：提交前退出、提交后退出、显式回滚、派生后外部修改、并发追加、超限压缩、文件缺失、非法操作。
- PostgreSQL 文件存储/S3 各 4 组：提交前后退出、回滚、并发追加；每次使用独立临时库，结束后移除。
- SQLite/PostgreSQL 各 1 组固定时序：保存提交后暂停原响应，由第二 API 删除算例，再释放原响应；断言原保存成功、恢复后的内容和 SQL 事件一致。
- 实际 Agent/mock provider 的保存和下一次模型请求注入：文件存储与真实 S3 均通过，不只调用内部写者。
- 修复提交后删除竞争后，双 API 的完整写入协调 SQLite 93 项通过；未声称此轮又重跑 PostgreSQL 全 93 项，PostgreSQL 使用上述定向故障证据。

SQLite 8 组证据不是一次绿色整套：前 7 组通过后，测试错误地把预期的文本 500 响应解析成 JSON，补跑最后 1 组通过。更早一次派生冲突夹具期待 500，实际正确返回 409；修正测试预期后继续。生产行为没有为通过测试而放宽。原完整写入协调回归暴露提交后删除竞态，保留失败日志；修复后的结果单独登记，不把初次失败算作通过。
