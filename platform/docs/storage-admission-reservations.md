本批承接 [存储用量核验](storage-usage-budget.md)，处理合作写入入口的跨请求竞争和分块上传的未来字节占用。N4-05 仍未全部完成：运行时文件增长、元数据/历史版本写入放大、宿主机缓存预算及长数据库事务治理仍需继续。

## 真实复现

在 1 MiB 套餐下，同一账户先后创建两个各声明 900 KiB 的分块上传，原代码都返回成功；实际只创建少量会话元数据，因此单次扫描看不见未来 1800 KiB 的占用。普通文本保存原来没有调用存储配额检查，2 MiB 文本也能直接写入。

原始观察为 `tmp/storage-admission-before-vo_6iam2/storage-admission-observation.json`，日志 `tmp/N4-storage-admission-before.log`。这两个入口现在都受到配额准入保护。

## 用户级事务准入

`storage_admission.lock_owner` 使用数据库事务协调同一用户的合作写入。PostgreSQL 使用独立命名空间的事务 advisory lock，竞争时立即返回 409 / `storage_quota_busy`，不在已经持有算例锁时反向等待用户锁。SQLite 使用用户行更新参加数据库写事务串行化，因此覆盖不同 API 进程，不依赖 Python 进程内锁。

`check_storage_quota` 在锁内读取套餐、未写入的上传占用和实际存量，然后判断新增字节是否可接纳。锁保留至调用方事务提交/回滚，不由检查函数提前释放。既有上传、算例复制、导入、工作副本封存等调用者由此共享用户级准入。普通文本保存新增相同检查。拒绝超额为 429，存量无法核验为 503。

这仍依赖调用者在同一事务内完成对应写入并等待 I/O 结束；它不自动约束原生求解器、外部客户端或尚未接入配额检查的写入路径。PostgreSQL 锁冲突可由客户端稍后重试；当前没有在服务端自动重放任意写请求。

## 分块上传额度生命周期

新增 `upload_storage_reservations` 表，绑定用户、算例、后端/存储位置、会话 ID、目标路径和声明大小，记录剩余未写入字节及 `active/completed/cancelled` 状态。其数据库迁移为 `8c61e3d702a9`，前序为 `7b50d2c6f198`。

1. 创建：在用户准入锁内检查全部声明大小，创建存储会话并在同一 SQL 事务中保存占用。只有事务提交后才返回成功。
2. 写分块：同时持有用户和算例协调锁，先核对真实会话偏移，再计算剩余字节。实际写入线程排空后才更新 SQL 进度；其他准入检查计算“实际存量 + 剩余占用”，不会把同一有效负载长期双计。
3. 回滚或进程退出：已落盘而未提交 SQL 的字节暂时与旧占用重复计算，保持保守。下一次写入在协调锁内核对实际偏移再推进，不按超时、进程重启或旧时间戳直接释放占用。
4. 完成：另检查两份新有效负载的复制空间，然后将完成事件、文件事务见证和占用结算放在同一 SQL 事务。重复完成使用原完成证明，不重复发布文件。文件事务备份、原生对象版本和元数据的全部峰值放大仍是后续预算任务。
5. 取消：存储清理结束后才把未来占用置零。若本地清理成功但 SQL 回滚，重试只有在绑定目录确实不存在时才结算；目录仍存在但元数据损坏不能当作已清理。远端取消沿用其持久 tombstone 与条件删除协议。已保留的实际字节仍由扫描计费。
6. 老会话：首次继续写入时核对真实会话，只有剩余字节可接纳才建立占用。老会话的已存字节由原存量核验计入；历史完成记录可继续幂等读取。

创建提交成功但响应丢失时，占用不会消失。新增授权接口 `GET /api/v1/cases/{case_id}/uploads` 返回该算例的活动占用，包含会话 ID、路径、声明大小、剩余字节和存储绑定是否匹配；调用者可据此找回会话，再调用原状态、续传或取消接口。原用量响应新增 `storage_bytes_reserved`，与 `storage_bytes_used` 区分。

## 部署和验收

新增表需要先执行项目正常迁移流程，代码不会隐式升级现有数据库。本次只对 `tmp_vf_*` 临时数据库执行迁移，不迁移开发数据库、不重载开发 API。回退迁移在表中存在任何活动或已结算历史时明确拒绝，避免静默丢失额度归属。

`storage_admission_smoke.py --postgres` 和附加 `--s3` 使用共享数据库/存储的两个实际 API 进程，覆盖跨算例超额、文本写入、外来算例拒绝、取消幂等、并发创建、写入后回滚、完成幂等、取消回滚、创建提交响应丢失、旧会话接续和真实进程终止后的续传。实际执行把相关断言汇总为每种数据库/后端组合 10 项。

首次 PostgreSQL 运行发现 `SUM(bigint)` 返回 Decimal，导致严格整数字节参数校验拒绝；已在数据库整数列求和出口作无损整数转换。失败记录保留，不能将其中 SQLite 通过部分当作整套双库通过。最终结果、迁移约束和原上传恢复兼容范围以 `tmp/mainline-storage-admission-evidence/validation.json` 为准。

## 下一步与边界

本批的持久占用只覆盖上传尚未物化的有效负载；复制/作业封存目前依靠事务内用户准入，尚不是跨长操作的完整持久额度账本。需要继续为它们建立包含工作副本、不可变产物及元数据的峰值预算，并对运行中的增长进行结算和限制。

扫描和复制期间仍可能持有数据库事务或算例控制锁，用户级串行化没有解决心跳争用。下一步必须把长 I/O 与短数据库控制事务拆开，并使用可验证的持久操作归属，不能简单提前放锁或按过期时间偷取仍在写入的操作。

活动上传占用没有任意 TTL；尚未完成统一过期回收策略和前端会话恢复界面。用户可通过既有取消 API 释放确定不再继续的会话。宿主机临时目录、S3 缓存、原生工作进程的空间限制及跨节点总配额仍未由本批完成。

本次复核还发现真实回收站使用 `_trash/users/{user_id}/`，位于当前存量扫描的 `workspaces/{user_id}/` 之外；这部分保留字节需要下一批补计，不能把用户前缀中的人工保留文件测试当作真实回收站已覆盖。移入回收站的上传仍保留未来占用，当前须先恢复算例再取消/继续上传；不因暂时无法访问算例而无证据释放额度。
