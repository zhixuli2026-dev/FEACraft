# S3 逻辑文件与不可变内容提交指针

2026-11-06，N2-06 第二十批。此批处理上一批真实复现的“API 退出后迟到写入越过恢复”缺陷。主线仍为 23 完成、11 进行中、19 待开始，剩余 30；没有据此关闭 N2-06 或全功能 295 项。

## 原因与当前协议

旧协议在远端真实文件名上覆盖内容。API 进程退出后，已经收到的 HTTP PUT 仍可能执行；恢复看到旧内容并清除 pending 后，旧请求还能写入新内容。上一批原始证据保留在 `tmp/staging-inflight-before.json`，不覆盖、不重新运行 before 脚本。

现在 `storage.s3()` 返回统一逻辑文件客户端。生产使用的两种算例前缀 `workspaces/{owner}/cases/{case}` 和 `workspaces/{owner}/cases/{uuid}/{case}` 均接入；非标准算例前缀在恢复入口拒绝可变访问，要求明确迁移。账户创建日志等非算例空间保留原接口。

- 新内容上传到 `.vibeflow/live-store/objects/{uuid}/{basename}`，使用条件创建，保留实际内容类型及其他对象元数据。
- `.vibeflow/live-store/head.json` 保存逻辑路径到独立对象的映射。它是永久保留的提交指针，每次转换均写入新的随机 nonce，并对旧指针 ETag 做条件更新。
- 文件事务的 pending 标记也是该清单中的一个逻辑文件，和数据选择处于同一个指针中。不会独立删除物理指针再重新使用空槽。
- 删除留下新的路径版本记录，读取和列举将其视为不存在。这样即使某路径经历“新建、删除、再次不存在”，旧创建操作也不能在合并重试时把它重新创建。
- 恢复在原有 SQL 算例锁或持久存储占用下先更新指针 nonce，再核对原有文件日志和 SQL 提交事件。回滚选择旧内容时仍创建新对象引用与新路径版本，不恢复旧指针字节或旧 ETag。
- 已发送的旧数据 PUT 最多留下未引用对象；已发送的旧指针 PUT 携带过期条件，存储端返回 412。进程退出仍用于判断能否接管 SQL 占用，但不再被当作远端请求已结束的证明。

这保证每次指针转换的完整性，不宣称 SQL 与对象存储是一个物理事务。多文件普通写入仍经历 pending 下的中间状态，由原有 SQL 见证决定保留或补偿；专业产物仍使用自己的不可变发布版本和活动指针。

## 读取、并发和旧数据

HEAD、GET、Range、下载签名、列表和分页统一解析逻辑文件；单文件版本使用独立的逻辑 ETag，实际对象读取再携带物理 ETag。相同字节被重写也获得新版本；其他文件变化不会改变本文件 ETag。签名下载固定不可变对象，后续编辑不改变已经选择的下载内容。

不同作业的日志可能并发发布到同一个算例。若 CAS 被其他路径更新抢先完成，存活的调用者只在目标路径身份完全不变时，最多重试五次合并；同路径变化或删除记录变化仍拒绝。重试发生在调用进程中，已经退出的进程不会替延迟 HTTP 请求重新选择指针。SQL/原生归属与线程排空要求继续由原调用层执行。恢复 fence 自身不盲目重试。

旧算例首次可变访问会完整读取并核对旧清单，将可变文件复制到独立对象，再以条件创建发布 head。head 存在后，不再回退读取旧物理路径，包括后来才到达的旧格式上传。受保护的 attempts、publications、上传块和不可变日志对象保留原布局；文件事务 pending 是明确例外。

后端必须实际执行条件创建/更新。客户端在发布 head 前用独有测试键验证条件失败及旧版本拒绝；不能把忽略 HTTP 条件的后端当作可用。head 最大 64 MiB，包含删除记录的路径数上限 100000；超限拒绝，不丢弃版本记录。

新私有目录受编辑保护，备份/导入/复制明确排除，常规列表隐藏物理对象。当前保留旧物理对象、旧内容版本和未引用上传；**本批未实现这些对象的完整垃圾回收和清单压缩**。删除记录不能未经协议处理便清除。它们继续属于既定存储清理、恢复和部署任务。

## 验证范围

规范证据入口：`tmp/mainline-N2-live-store-evidence/`，以 `validation-summary.json` 和 `source-binding.json` 为准。

1. 真实 HTTP 代理拦截已经收到的 S3 请求，终止实际 API owner，再由另一个 API 恢复。覆盖数据上传、pending 发布、更新、删除、回滚恢复旧内容、已提交事务的 pending 清理；检查恢复后的新编辑仍保留。
2. 另有“恢复后不编辑就放行旧请求”的更新/pending 场景，避免后续编辑本身使旧 CAS 过期而掩盖恢复缺陷。SQLite/PostgreSQL 都验证。
3. 直接适配检查覆盖旧内容迁移后迟到旧格式写入不可见、元数据与 Range、同内容的新版本、分页/子目录、固定下载版本、不兼容后端拒绝、不同文件真实 CAS 竞争和同文件竞争，以及创建/删除后的空状态竞争。
4. 兼容检查包括原 staging 崩溃窗口、普通文件及字典日志恢复、上传断点/提交恢复、创建恢复、产物别名版本检查、备份格式和实际下载 API。
5. 真实几何、网格、求解、后处理与 Pandoc 报告流程，以及新 API 的当前/历史引用通过。测试证据是增量组合：完整流程通过后补入删除版本记录，并以最终双库 HTTP/适配矩阵验证该变化；不宣称所有专业处理器或全部部署矩阵已在同一源码时点重跑。

原始失败均保留：HTTP 夹具曾误用未设置的 peer.case_id；PostgreSQL 夹具曾错误假定物理前缀不含防重用 UUID；同时启动的 WSL 测试服务撞上临时端口，已改用不在本机 WSL 临时端口范围内的隔离端口。全流程曾出现日志上传 ClientError；受控并发验证确认不同路径会竞争 head，增加有条件的合并重试后重跑通过。原失败请求没有记录完整存储错误响应，因此不把后续成功描述为取得了该请求的全部底层诊断。

## 后续与部署边界

开发数据库和端口 8000 未迁移或重启，验证均使用隔离数据库和真实临时 S3 服务。代码/数据格式升级须让全部 API/worker 使用相同适配协议；旧版本客户端不能与新客户端混用，也不能直接回滚代码后把旧物理路径当作当前文件。

下一步先按 N2-06 原验收条件核对文件提交前后、SQL commit 前后的覆盖及真实缺口，避免把其他阶段的 UI 或全量部署条件不断加进该项。剩余要求保持在原 53/295 计划中：普通保存/旧诊断/启动克隆的事务内 IO，旧数据的诊断隔离、已提交缓存重建、未知提交与历史排空失败、索引对账、原 UDF 单次 409 归因，以及跨主机和完整部署验收。新产生的不可变版本清理和清单容量问题也须落实到原存储维护范围，不能用永久保留所有对象宣称交付完成。
