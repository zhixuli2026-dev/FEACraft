# 同算例 UDF 批次

原 `POST /cases/{case_id}/jobs:batch` 的 `operations` 增加 `kind: "udf"`，成员提供 `run_dir`、`name` 和预算。MPI 与 UDF 使用按 kind 区分的请求模型，各自拒绝另一种操作的参数；原 commands 和 MPI 请求的规范化内容及摘要保持一致。

UDF 成员接入原有 `udf.integrate` 注册处理器、Job/attempt、持久批次投递和真实 Redis worker。先通过原构建入口生成可验证的本地 ELF 库，再将同一库与各工况输入完整封存。本接口不把尚未构建的库当成已存在，也不声称在准备运行批次中实现了构建依赖 DAG。

集成运行的 CDLL 加载日志改为各自运行目录中的 `udf-load.log`，避免同名函数的两个工况争写共享 UDF 目录日志。历史配置仍按原路径校验；构建日志保持原路径。控制字典的注册修改仍绑定准备时生成的精确内容。

真实 CDLL 与 icoFoam 进程通过有界 strace 记录实际文件查询。完整封存目录始终可见，原始清单保留为 origin_source；来源投影包含实际读取、缺失查询和目录枚举。加载与求解分别绑定其实际初始工作目录。控制字典的合法派生内容由配置绑定，来源仍保留修改前的原始摘要。系统外部文件只记录观察，不承诺完整外部依赖闭包。

正式 UDF 工作流保留原编译来源、工程状态和固定库/网格引用，新增运行期查询来源。固定引用重验通过后按实际挂载记录检查，不用可变兼容文件替代不可变版本。旧清单继续使用原契约。
