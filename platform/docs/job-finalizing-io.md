## 实现与结果边界

`jobrunner` 将旧求解证据计算及 sidecar 写入、staging 同步、日志读取/解析/JSON 序列化和成功后的 staging 清理放到工作线程。每项用 `finish_before_cancel` 等待不可取消的线程完成；即使外层任务被重复取消，也先排空当前读写，再关闭日志、处理异常或离开作业监督。

日志摘要先在短数据库会话中读取 case、存储前缀、日志路径和已有摘要，关闭会话后解析。写回使用数据库条件更新：这些绑定及旧摘要仍匹配才保存。解析期间改日志路径、存储前缀或摘要，不会被旧结果覆盖。摘要解析失败仍属于可选增强失败，不把已经执行成功的作业改成失败。

持久终态提交前，心跳与跨实例取消可以继续运行，最终仍以原有 `job_execution.finish` 的数据库结果为准。证据校验或同步失败保持现有失败原因，失败同步保留 staging；这里没有新增跨对象事务、上传回滚或自动重试。

底层 staging 清理仍沿用 `rmtree(ignore_errors=True)` 的尽力清理契约。专项初次 PostgreSQL 运行曾留下空 `Ref` 目录；测试原来把线程排空等同于目录必定消失，导致断言失败。现分别记录清理调用返回、保留原因和残留路径；不把忽略删除错误包装成可靠清理。删除错误可观测性与遗留目录对账继续纳入 N5-03。

持久结果已经提交后，可选清理被取消会等待清理线程退出；`_run` 保留已提交状态，不改成 `finalization_failed`，也不补发失败结束通知。终态提交前直接取消后台任务，则线程排空后仍暴露收尾未完成，保留 `finalizing` 等待恢复；不伪造成功或已持久保存的停止回执。此项恢复属于 N5-04。

## 验证范围

`job_finalizing_io_smoke.py --postgres` 在隔离 API、临时数据库和独立目录中验证以下窗口，完整结果与来源在本单元规范证据目录保存：

- 日志路径、存储前缀、摘要三种并发更改拒绝旧摘要覆盖。源文件保持不变，正常求解证据包含实际生成文件的哈希。

证据测试使用真正启动的 Python 进程与明确标识的 OpenFOAM 格式日志、网格/场文件占位数据，只验证 I/O 和证据流程，不是一次真实 CFD 数值求解。staging 使用真实复制及同步逻辑，但显式上传/删除函数指向隔离文件系统；不声称完成真实 S3 网络故障验收。响应耗时为指定屏障下单次观测，不是生产 p95。
