## 2026-11-18 目录树恢复的空间准入

本地目录树事务通过同卷重命名归还旧树或保留已提交的新树。此前，SQL 没有提交时，恢复代码先移动目录，再为写回执申请固定的 16 KiB。若此时额度不足，接口会报告失败，但磁盘上的目录已经变化。现在先编码实际回执，为这段字节同时检查工作区所有者额度和节点额度，两项都通过后才开始移动文件。

SQLite、PostgreSQL 各搭配本地文件存储，从正式恢复接口处理两种真实 SQL 结果。每个算例将原文件替换为含 128 个二进制文件的目录，并增加一个空目录和权限记录。验收分别保留或回滚数据库事务，产生磁盘上等待判定的真实目录事务。首次验收准备路由漏写 API 前缀，返回 404，修正后两种数据库均通过。

| SQL 结果 | 所有者余量少一字节 | 余量恰足 | 重试结果 |
|---|---|---|---|
| 回滚 | 212 B，返回 429 | 213 B，恢复原文件与原目录结构 | 同一回执只有一份 |
| 已提交 | 210 B，返回 429 | 211 B，保留新文件、空目录及权限元数据 | 同一回执只有一份 |

两种结果都另外在所有者余量恰足时触发实际节点限额，均返回 `409 node_storage_full`。每次拒绝前后逐项核对项目子树和待恢复目录，文件路径、类型和内容摘要相同。这里的字节数对应项目逻辑用量，节点同时保持配置的磁盘最低可用空间。以上覆盖本地目录事务，S3 目录写入走独立的对象事务。[SQLite](../../tmp/live-cli-startup-j2pq7mc5/tree-budget.json) · [PostgreSQL](../../tmp/live-cli-startup-064xoyjr/tree-budget.json) · [验收入口](../server/live_llm_tree_recovery_budget_acceptance.py)

## 在复制前计算峰值

新事务先冻结变更条目，只读核验现有文件和 `FileSource` 的长度、摘要、路径及前置条件，生成完整计划和预先确定的事件 UUID。准入前不创建准备目录，不复制 before/after 文件，也不写业务提交证明。

分配量包括全部 before/after 副本、实际编码的 manifest，以及顺序替换过程的最大额外空间。每次原子替换先完整写出临时文件，旧目标在替换前仍存在；替换后按新旧长度差累计占用，删除释放的空间也按实际顺序计算。最后写入 resolution 的临时文件同样计入。新事务采用较长的回滚状态编码预留收尾空间。

通过准入后，重新核验并复制文件。复制流按已准入的长度设上限，复制完成必须匹配先前摘要；源文件在观察后变大或改变时，不会继续复制超过预留的字节。目标替换仍使用原有前后内容核验及原子替换协议。计划超过可读取的 1 MiB manifest 上限时，在分配前拒绝。

## 账户锁、节点预留和取消

账户额度属于算例所在工作区的所有者。检查使用调用者的 SQL 事务，不单独提交业务，也不启动第二个 SQLite 写事务。PostgreSQL 在已经持有算例锁时尝试获取账户锁，冲突返回繁忙，避免等待形成锁顺序循环；SQLite 使用同一个父事务串行化写入。

账户锁保持到调用者提交或回滚。节点预留覆盖所有复制、manifest 写入和替换线程，直到 I/O 排空才释放。取消不会让仍在写入的线程失去预留。进程退出后，已有文件仍进入实际用量盘点；节点预留按既有进程出生身份核验回收，不按时间猜测释放。

## 恢复也需要空间

恢复先完整核验 pending 计划、SQL 提交证明和当前内容，再针对真正需要回滚的文件计算替换临时文件峰值，并加上 resolution 写入。账户或节点空间不足时保留待恢复证据与当前文件；额度恢复后可再次执行。

已提交事务只补齐收尾记录，不重写正文。没有 pending 的读取仍直接返回，不取得新的额度或节点预留。调用者自己尚未提交的事务保留原有身份判断，不把当前会话可见的提交证明误认为已持久提交。

## 验收与边界

新增压力检查覆盖 before 副本、after 副本与替换临时文件、空正文的元数据、节点容量、FileSource 复制及检查后增长、实际替换峰值与跨进程锁、取消排空，以及进程死亡后恢复分别被用户额度和节点容量拒绝、再成功重试。兼容检查覆盖普通文件、字典/历史和断点上传安装的中断与提交状态。

- 这是共用文件事务的文件长度预算和合作进程准入；它不强制约束绕过该服务的原生进程、外部程序或目录外写入，后者仍属 RB-17。
- 只读扫描额外增加一次摘要核验；锁内长 I/O、取消后的期限与有界队列仍需 RB-14 治理。
- 已准备但未成为 pending 的目录、历史副本和未知外部改变继续保留并计费，清理协议仍属 RB-15。
- 源文件的外部改变可能使本次事务失败；已完成的部分副本仍计入实际用量，不能用删除未知文件来回避超额。
- 本次没有把 S3 读取隐含恢复、全部其他写入入口、ZIP/备份/导出等长文件操作自动视为覆盖，剩余范围继续由 RB-12 跟踪。
