## 已实现的行为

本地 `fs` 存储的普通文本保存、16 MiB 以内的普通上传和单文件删除，先保存修改前后的内容，再修改工作文件。数据库事务中的 `files.transaction_applied` 事件记录事务 ID 和计划摘要；事件与业务更改、原有文件变化事件同属调用者的 SQL 事务。没有新增表或修改开发数据库。

日志位于算例的 `.vibeflow/file-transactions/`。准备目录使用独立 ID；内容和清单写入、刷新后，无覆盖地原子移动到 `pending`，之后才修改工作文件。每个算例同一时刻只允许一个未解决的日志。服务支持最多 256 个文件。首批修改前后备份合计限制为 1 GiB；后续[分块上传事务](upload-transactions.md)将本地限制扩为单文件 1 GiB、前后备份合计 2 GiB，以保留原 1 GiB 覆盖上传能力。S3 的后续流式适配也已使用相同预算，见 [S3 上传事务](s3-upload-transactions.md)。复制与摘要校验使用流式处理；普通 API 当前每次只提交一个文件。

协调器获得算例数据库锁后，在文件预条件检查和读取前处理 `pending`。正常提交后也会完成这一处理，再返回成功：

| 数据库证据和当前文件 | 处理 |
| --- | --- |
| 提交事件不存在，文件仍为旧内容 | 保留旧内容 |
| 提交事件不存在，文件为此次写入的新内容 | 还原旧内容；撤销创建或恢复删除 |
| 提交事件已持久化，文件为新内容 | 保留新内容，不重新写入 |
| 文件为第三种内容，或已提交文件又被修改 | 返回 `409 file_recovery_required`，保留现场 |
| 清单、备份内容、路径或存储绑定无法验证 | 返回同一恢复冲突，保留现场 |

恢复先验证全部备份和全部目标，再执行所需补偿。补偿中再次退出可继续恢复。当前 SQL 事务自己刚写入的事件不算已提交证明，嵌套协调读取不会提前清理日志。完成后将日志移入 `history/{transaction_id}`，保存判定回执。历史目录和准备目录暂不自动清理。

文本、文件版本、二进制元信息、文件树及 raw/Range 下载进入相同协调器。新增只读 `GET /api/v1/cases/{case_id}/file-transactions`，在正常读取因冲突被拒绝时仍可查看 `idle`、`pending`、`conflict`、`journal_invalid`；有效日志还显示 SQL 提交状态和各路径的前后版本匹配状态，不返回备份内容。S3 明确返回 `not_supported`。

普通写入不能编辑日志命名空间。算例/工作区复制、用户备份和备份导入排除事务日志，避免把原算例的事务身份带到新算例。复制和最终来源校验共用排除规则。

## 验证与发现的问题

- `file_transactions_smoke.py`：SQLite 14 组真实 API 终止/新进程恢复，包括日志发布前、文件修改前后、SQL commit 前后、创建、删除、多文件中断、补偿中断、正常回滚、外部修改、损坏备份和普通 API。
- PostgreSQL 9 组关键场景使用新建的临时数据库，完成后删除；涵盖提交前后、文件修改前后、多文件、补偿中断、冲突及正常 API。
- 两库分别补充同一 Session 的未提交事件、嵌套读取、显式回滚后恢复，均通过。首次夹具忘记刷新回滚后过期的 User ORM 对象，修正夹具后通过；未据此修改产品逻辑。
- 既有双 API 写入协调回归 SQLite 93 项通过，包含复制、工作区复制、备份、附件、分块上传及会话竞争。首轮发现新日志被复制；修正后又发现工作区复制的最终校验漏用排除规则，两处均修复，保留失败记录。
- 下载一致性 fs 17 项、模拟协议异常 6 项及离线备份清单 20 项通过。

正式证据目录：`tmp/mainline-N2-local-file-transactions-evidence/`。上述验证是增量证据：没有声称所有部署环境、S3、Linux 文件系统和所有专业入口在本次全部重跑。

## 下一批工作及边界

1. **caseDict 多文件事务**：同步字典正文、Case 镜像、修订记录及文件事件；包括阶段推进和重算时的阶段回退。当前专用字典写者尚未接入此日志。
2. **其他写入口**：分块上传完成、Agent/提案文件写入、导入/复制的目标前缀等。它们会先处理已有日志，但自己的修改尚未获得本批普通文件日志保证。
3. **S3 恢复**：条件写入/删除、远端持久日志、未知 SQL 提交及无本地缓存的恢复；本批保持原有 S3 普通文件行为。
4. **恢复运维**：启动扫描、孤立准备目录、历史日志保留/清理、存储配额和诊断界面；目前在下一次协调访问时恢复，备份占用仍计入实际本地磁盘使用。
5. **索引与事件消费者**：文件恢复不等于索引同步原子提交，继续 N6-02 的持久对账和修复；本批未声称消除所有索引短暂不一致。
6. **原保留项**：旧发布准备目录、未完成上传、UDF 当前引用单次 409 根因，以及原 N2-06/FF-J15 的完整恢复验收，继续保留。

此协议依赖所有合作方使用同一数据库算例锁。哈希检查可发现已观察到的外部修改，但不是针对任意宿主进程的操作系统级 compare-and-swap；不能宣称消除外部进程在最后检查和替换之间的竞态。已测试的是进程终止和数据库提交窗口，不是任意磁盘掉电损坏。

遇到冲突，不应删除 `pending` 或手工把事件标为已提交。先保留当前文件和日志，用诊断接口查明提交状态；人工选择版本和历史恢复界面仍属后续工作。源代码回退使用上一批 `mainline-N2-publication-consistency-20261105.zip` 恢复到新目录；若已有待恢复日志，应先处理现场，旧代码不具备本日志恢复能力。
