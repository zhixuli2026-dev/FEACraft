# 作业日志诊断与失败归档恢复

2026-11-17，N4-05 / RB-14 子阶段。主线 49/53、剩 4 项；资源清单 11/17、剩 6 块；295 项全功能目标保持。Claude 已按用户要求停止推进。本阶段没有模型调用，也没有模拟 LLM。

## 用户可见行为

作业实际超时或输出超限时，诊断现在会在封存日志之前写入文件，运行时和重启后的两种 SSE 均可读到。诊断额外缓冲合计限制为 65,536 字节。旧 SSE 不再因改用文件分页而漏掉原来只保存在 `JobProcess` 内存里的提示。

日志已关闭后才发生的收尾错误，通过旧 SSE 的独立诊断事件传递，不修改已捕获日志、摘要或字节游标。带 offset 的接口保持原始字节语义；两种流都返回 `persistence_failed`，不会把收尾失败报成成功 done。此类晚到诊断目前依赖本地 JobProcess，未宣称可跨 API 重启重放。

历史默认日志路径恢复为与执行器一致的 `.vibeflow/jobs/job-{id}.log`；已明确保存的现代 `.vibeflow/job-logs/` 路径继续按记录读取。

## 失败作业的 S3 恢复

真实超时触发后，原执行预算可能已耗尽，不能再发起归档上传。这次测试暴露了三个连贯问题：公开接口认为失败作业可恢复，但底层容量准入只接受运行中收尾/取消；归档完成后日志仍可能指向旧位置；更新归档元数据会使原 v2 排空证明的快照摘要失配，导致同一算例后续作业被拒绝。

现在显式恢复路径允许已停止的 failed/interrupted 作业补传原捕获输出，继续验证账户、算例、attempt、执行 head、claim、输入/输出清单、原停止证明和原 API 确切退出凭据。额度、未知写入者保留和归档完成验证仍沿用现有实现。原 API 活着时仍返回 409；恢复不重跑命令，也不将失败作业改成成功。

归档完成事务把失败日志指向已验证的 `run/.vibeflow/finalizing/root.log`。已有归档事件但保留旧日志指针的记录，可以通过重复显式恢复幂等修正。

v2 排空快照只允许因同一事务中的归档完成事件更新 `output_manifest_json.object_store`。其他快照字段、原停止记录、原 owner 退出凭据及清理历史保持一致，事件记录更新前后摘要；其他版本仍须通过原验证。最终测试在同一个算例继续提交真实作业，确认归档恢复后能正常进入下一次执行。

## 实际验收

| 场景 | 证据 | 结果 |
| --- | --- | --- |
| FS：真实 10 秒超时、1,024 字节输出上限、关闭日志后的受控收尾故障 | `tmp/job-log-diagnostics-fs-qw_nczrd/diagnostics-result.json` | 3 个真实作业场景；资源诊断重启读回通过；晚到错误不改变日志摘要 |
| S3：同样三种场景，实际 API 退出后恢复归档，再在同一算例继续作业 | `tmp/job-log-diagnostics-s3-cjthokn8/diagnostics-result.json` | 活 owner 恢复被拒绝；真实补传、旧指针修复、原排空证明保留、重启两种 SSE 读回通过 |
| FS 正常完成、实际取消、API 重启后的完整读取/分页/尾部/SSE | `tmp/job-log-fs-lifecycle-ef0r8nmn/fs-log-result.json` | 2 个真实作业场景通过 |
| S3 正常输出、重启读取、4 个实际阻塞读取、429、断连排空、30 秒预算后 504 及恢复 | `tmp/job-log-range-capacity-5oc8rtut/range-result.json` | 1 个真实作业场景通过；日志请求没有保留数据库连接 |

合计 9 个真实作业场景，包含 2 个主动注入收尾故障的场景，不能称作 9 个作业成功。诊断场景的 6 个根进程分别独立核验退出；其余正常/取消场景核验原停止证明。9 次实际 API 退出均有出生身份观察，相关 S3 测试服务已停止。

FS 诊断使用 `N4-05-job-log-diagnostics-review-v2-20261117.json`（648 份源码）；S3 诊断使用 v6（649 份）。其后的生产修改针对 S3 归档准入和排空快照，未改 FS 诊断所验的执行器、路由及日志读取代码。最终 FS 兼容使用 `N4-05-job-log-final-FS-review-20261117.json`，最终 S3 兼容使用 `N4-05-job-log-final-S3-review-v2-20261117.json`，各 649 份源码。不能将早期 FS 诊断描述为在最终源码上重新执行。

S3 超时/输出超限时，本地最终文件分别为 252 / 1,317 字节；封存日志分别为 89 / 1,152 字节。差值来自封存之后的本地上传/工作区错误提示。恢复按原捕获文件的大小和摘要验证，不追加晚到文字到不可变归档。

容量检查观测真实 SQLAlchemy checkout/checkin 的请求归属。最终断连观测中总池占用为 1、日志请求占用为 0，后台数据库工作不能被误计为日志连接泄漏。4 个真实读取仍保持容量，断连不提前归还名额；释放后响应体关闭，后续请求恢复。同步读取须实际排空，30 秒预算不是可强杀同步 I/O 的响应硬期限。

- `job-log-diagnostics-s3-a53bmf9p`：真实恢复被拒绝；随后只对其隔离副本继续诊断。诊断前数据库/日志及各轮源码保留。
- `job-log-archive-diagnosis-ork10052`：定位终态恢复被容量准入拒绝；`job-log-archive-diagnosis-x1efma3z`：修复后真实归档通过。后者报告残留的 `actual_error` 来自前一轮文件，`prior-error-file-clarification.json` 用文件时间及 API 出生时间澄清，原报告未覆盖。
- `job-log-diagnostics-s3-rm5ynjg4`：归档与指针修复通过后，下一作业因旧排空快照失配返回 409，随后修复事务内绑定并在最终 S3 诊断重新验证。
- `job-log-range-capacity-05102quy`：容量测试误要求整个数据库池为空。最终测试改用已存在的真实请求归属观测，保留总池读数、并发上限、超时条件和这次失败源码。

完整汇总与最终源码归档见 `tmp/mainline-N4-05-job-log-diagnostics-evidence/validation.json` 和同目录 `reviewed-sources.zip`。测试为真实进程、FS/S3 基础设施及受控故障；真实模型 0、模拟 LLM 0、Claude 0。
