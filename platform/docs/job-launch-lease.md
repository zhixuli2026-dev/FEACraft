## 两个实际问题

1. `claim_job` 提交后，到 `JobProcess.start` 完成才创建心跳。隔离 API 中配置 10 秒租约，在准备阶段暂停 12 秒：heartbeat 与 lease 均未改变，最终放行因过期被拒绝，Job failed、payload 未启动、实际准备范围已退出。证据：`tmp/launch-lease-before-0zx4t7ea/before-result.json`。
2. `runtime_workspace` 持有 case 写锁时读取并哈希封存输入和工作副本。实际冻结文件校验暂停 8 秒后，另一 API 的持久取消耗时 8.172 秒。证据：`tmp/workspace-lock-before-kctao4f6/before-result.json`。原夹具最初错误要求提交一定返回 409；取消被锁挡住时，启动也可能先返回 200。修正为记录实际 200/409，并核对取消等待与最终状态；未修改产品来制造特定顺序。

## 实现

`job_launch_lease.LaunchLease` 在领取成功后监督独立的启动任务，按现有可配置间隔续租，并在准备及启动边界作同步核对。持久取消或心跳失败会停止本次启动；取消与所有权失败分别保留原有状态/停止原因。进入 `JobProcess` 后交给已有运行及 finalizing 心跳，启动监督任务被等待并回收，`JobProcess` 不保留启动 guard。

staging 复制、准备目录和旧求解输入快照移到工作线程。任务取消后，仍等待不可取消的线程完成，再处置本次新建准备副本和保存失败/取消状态；不会让复制线程在已返回的请求后继续写入。此处只处置本次已知分配且尚未执行原生命令的副本；实际执行后保留 staging 的既有失败诊断规则不变。

`runtime_workspace` 分三步：短事务核对 claim 并取得数据库输入清单与 case 前缀；锁外读取封存输入、工作副本、目录及文件哈希；重新取得同一 case 锁，复核 claim/head、完整输入清单及前缀，再验证发布来源并提交输出清单。输入来自受保护的 attempt 目录，未改为信任 live-case 别名或磁盘自述清单。读取期间更换输入绑定或改动工作副本会拒绝启动。

发布依赖的 `publication_inputs.validate` 仍保留其原有锁内来源/当前版本复验；本单元没有削弱来源校验，也没有声称所有发布处理和对象存储收尾均已移到锁外。

## 验证

`job_launch_lease_smoke.py --postgres`：SQLite/PostgreSQL 各 18 项通过。

- staging、封存工作副本、Windows/WSL 原生准备、finalizing 输出校验各暂停超过租约长度，仍观察到持续续租，且真实 payload 只执行一次。
- staging、工作副本、原生准备、已登记未放行、finalizing 五个边界，跨实例取消和心跳故障均覆盖。非取消线程未结束时，准备请求不提前返回；随后核对持久终态及实际范围退出。
- 锁外读取期间修改输入清单或工作副本，拒绝启动且源文件保持不变；失败启动的心跳不继续运行。
- SQLite 本次五个取消提交样本分别为 0.125、0.032、0.031、0.016、0.047 秒。这是明确夹具下的单次实测，不是生产 p95 或完整性能基线。

staging 专项使用真实文件复制和上传逻辑，但将上传适配到隔离本地文件目录；没有真实 S3/Redis 服务故障。第一次夹具误读公开 case 返回字段，尚未启动 Job；第二次未重定向 staging 的显式 S3 上传函数，因本地对象存储端点不可达失败。纠正夹具后完整重跑双库；原日志保留。
