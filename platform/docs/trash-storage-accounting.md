# 真实回收站用量与移动期间的计量（N4-05）

## 2026-11-21 盘点期间的写锁等候

回收站处理算例及工作区删除、恢复时，先结束授权读取的事务，再等待盘点使用的系统锁。进入工作区和算例写事务后只尝试一次系统锁。如果刚好有新盘点获得锁，请求返回 409 并释放数据库写锁，用户可重试。实际移动仍由系统锁、工作区与算例锁共同保护，取消会等待已开始的文件移动排空。 [回收站服务](../server/app/services/trash.py) · [公开接口](../server/app/routers/workspaces.py)

隔离 API 在真实盘点持锁时提交实际算例删除。原版独立 SQLite 写入等待约 0.922 秒后因数据库锁失败，新版约 0.016 秒提交。实际创建盘点在预检返回后先获得锁时，删除返回 409，同一盘点期间仍可写 SQLite，重复删除和恢复均保留原文件。 [旧版对照](../../tmp/trash-wait-budget-sl1m69lw/trash-wait-result.json) · [新版计时](../../tmp/trash-wait-budget-xevraa62/trash-wait-result.json) · [抢锁专项](../../tmp/trash-wait-budget-mxhxhdrf/trash-wait-result.json)

SQLite 和 PostgreSQL 各通过 11 项真实计量及故障检查，包括双 API 的移动、取消、持锁进程退出和计量恢复。4 组公开 API 场景和 7 组 Windows 文件系统回归也通过。双库回归首次因观察器未转发已新增的扫描参数停止在夹具创建，补齐参数转发后通过。模型调用 0。 [双库计量](../../tmp/trash-storage-evidence-u4pyaei_/result.json) · [公开 API](../../tmp/trash-public-routes-q92ir6xx/trash-public-routes.log) · [专项入口](../server/trash_wait_budget_acceptance.py)

本批修复本地回收站保留文件未计入用户存储用量的问题。它承接[用户级准入和上传占用](storage-admission-reservations.md)，不改变回收站删除/恢复协议，也不代表完整磁盘资源治理已完成。

## 复现与实际目录

项目真实回收站将算例移入 `_trash/users/{user_id}/cases/`，整个工作区则移入同一用户的 `workspaces/` 子目录。原扫描只覆盖 `workspaces/{user_id}/`，因此真实删除后仍保留的数据没有计费。

隔离 API 复现中，普通文件连同保留的事务资料在删除前计量为 4,199,214 字节，调用真实删除接口后只剩 1,759 字节；回收站中原文件本身仍有 2,097,152 字节。原始证据为 `tmp/trash-quota-before-gt9e7nfd/trash-quota-observation.json`，日志 `tmp/N4-trash-quota-before.log`。

`storage_usage._scan_fs` 现在扫描两个物理用户根：活动工作区和 `_trash/users/{user_id}/`。沿用相同的条目上限、时间预算和普通文件/目录身份核对；不跟随 junction、symlink 或其他 reparse point。不读取回收站索引来决定哪些字节应该计入，所以索引尚未提交或遗留的无索引文件仍收费。相邻用户目录不混入统计。全局索引/锁文件不属于某个用户的数据，未摊入用户字节数。

## 并发移动与扫描取消

分别扫描两棵目录仍会有竞争：先扫描活动目录后，一个恢复操作把文件从回收站移回已经扫描过的位置，会使文件两边都未被计入；相反方向可能重复计量。

两棵目录的完整扫描现在持有回收站原有的进程内锁和 OS 文件锁，与删除、恢复及索引保存失败后的移动回滚互斥。此锁覆盖所有使用该存储根的 API 进程。扫描不依赖时间戳猜测移动是否结束，也不会把锁文件残留当成活跃写入者；进程退出后由 OS 释放实际锁。

`trash._mutation_lock` 新增可选绝对 deadline，进程内排队和 OS 锁排队都使用同一截止时间；普通回收站操作仍采用默认 30 秒预算。扫描超时返回无法核验，不返回零。扫描线程放到事件循环之外；请求取消也必须等待其实际线程退出才释放移动锁和扫描槽位。

当前锁粒度是整个本地回收站，多个用户的存储扫描和回收站移动会串行。这保障合作移动下的计量一致性，但尚未优化为每用户并行；也没有让所有外部写入或原生作业参与同一快照协议。操作系统中已经阻塞的文件调用仍不受硬终止保证。

## 验收范围

`trash_storage_usage_smoke.py --postgres` 使用同一存储和数据库上的两个真实 HTTP API 进程，在 SQLite/PostgreSQL 各检查 11 项：

- 算例进入回收站后，实际字节和未物化上传占用仍保留；降低套餐后不能借删除绕过准入。
- 恢复后用量一致，原上传可继续取消并结算；整个工作区的删除/恢复也保持计量。
- 无索引保留文件收费，相邻用户排除，回收站 junction 拒绝且外部数据不变。
- 两个 API 之间的恢复和删除无法穿过两段扫描形成空窗或重复计量。
- 扫描取消后，移动仍须等待线程排空。
- 进程内及跨进程锁等待均遵守扫描预算，随后容量恢复。
- 真正终止持锁 API 后，另一 API 可以核验完整存量。

另运行原回收站 OS 锁/无覆盖移动 7 项，以及原本地存量预算 8 项兼容检查。最终进程结果、临时库清理和源码绑定见 `tmp/mainline-trash-storage-evidence/`。本批不修改 S3 代码，没有用这些本地测试扩张 S3 验收结论。
