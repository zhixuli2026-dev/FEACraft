# 损坏上传现场的保留与隔离

2026-11-10，N5-07子阶段。元数据损坏、元数据缺失及部分字节的上传，可以从“服务端未完成上传”进入原始现场核查，复用现有文件版本的登记、隔离、候选预览和明确新编辑。FS/SQLite四组、S3/SQLite三组及实际S3浏览器已有下述证据。主线仍38/53完成、剩15，N5-07原四条和全部295项目标保持。

## 用户操作

上传列表中无法核验元数据的记录保留进度未知说明，并提供“核查原始上传现场”。点击会打开同算例的“文件版本与人工恢复”，选中明确的上传ID。页面说明：上传完整性尚未确认，隔离关闭原上传入口，保留内容继续占用存储；之后恢复暂存文件只是一份明确的新编辑，不能当成原上传完成。

“登记保留原版本”保存原因、原位置与快照，不放松写入限制。“确认隔离此版本”保留实际暂存文件、损坏JSON及特殊条目，原目标不变。用户可在已完成隔离记录中选择普通暂存文件，预览真实内容，明确目标和原因后按原目标摘要约束提交新编辑。链接和特殊条目只登记自身观察，不能当作普通文件读取或恢复。

隔离确认在发送前保存原key/body。若请求遇到写入结算冲突，或实际提交后响应丢失，页面保留同一次确认；刷新并重新选择原算例后可继续读回原结果，不创建第二次隔离。长面板通过现有项目区滚动访问；本批没有宣称完整移动工作台验收通过。

## 协议和关闭原入口

原文件恢复API新增明确来源`uploads/<32位小写十六进制ID>`，例如`GET /api/v1/cases/{case_id}/file-recovery?source=uploads/<id>`；其余操作仍使用既有file-recovery/actions、候选读取和restore-plan。服务端不尝试从损坏JSON猜出原文件名或完整内容，不重放旧上传。

FS用有界、不跟随链接的原始目录快照，并无覆盖移动到私有隔离目录；S3逐对象记录条件身份和摘要，复制独立保留版本，读回核对后封闭旧目录版本并关闭原逻辑对象名。原清单和副本均保持，迟到的旧目录条件写入不能复活原上传。遗漏在清单外但已登记的分块写入键继续使用既有永久关闭机制；其网络操作在释放短SQL控制锁后执行。

隔离和永久关闭证明在同一个SQL提交中保存，绑定账户、算例、原上传ID、存储位置、人工确认和完整来源快照。复用DurableEvent/outbox，不增加数据库表或迁移。原上传未来的payload占用在关闭后取消，实际保留字节继续由库存计量；不改另一写入者的活动额度或伪造停止证明。正常分块、状态查询及完成入口会核对该关闭记录，即使旧上传缺少原SQL额度行也不能绕过它继续写入。

原存储绑定与SQL额度归属不匹配、未知或活动的原写者、已有隔离证明等限制继续有效；可读的现场可先登记保留，再核查阻碍。上传入口自身是目录链接或特殊条目时，只观察该入口自身属性并允许登记保留，拒绝跟随读取或移动。普通目录中的硬链接/重解析点等条目只记录元数据。

原有单文件1 GiB、清单512条及总量2 GiB等有界检查继续；超限不会被当作空目录或授权自动处置。部分复制/关闭过程中再次变化的完整时序、全部部署/权限/数据库组合仍由原故障矩阵验收，不能用“先变化后确认被拒绝”替代所有交错。

## 保留的失败与修复

FS首轮`tmp/damaged-upload-FS-yq788zne/damaged-result.json`保持false。实际发现Windows的DirEntry缓存报告硬链接数0，而Path.lstat报告2，导致硬链接被误当普通文件后整份现场拒绝。现已使用不跟随链接的真实lstat属性分类；原生观察另存`tmp/N5-damaged-upload-Windows-link-observation-20261110.json`。重跑实际硬链接、符号链接和目标保持场景通过，没有删除或跟随这些链接来绕过验收。
