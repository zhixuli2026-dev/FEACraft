## V22 浏览器断网与刷新

2026-11-18，Chromium 打开一个正在运行的真实命令后离线并断开事件连接。命令在断线期间以退出码 7 结束。恢复网络后，浏览器以此前的游标请求事件页并读到失败事件。将真实事件通知逆序和重复投递，再次对账并整页刷新，页面仍显示原作业和原尝试失败，外部启动标记只出现一次。两种存储分别完成实测，每轮各有两次真实 DeepSeek 请求。[文件存储证据](../../tmp/live-cli-startup-ihfmai5m/browser-replay.json) · [S3 证据](../../tmp/live-cli-startup-4p61ae98/browser-replay.json)

N6-01基于N1-06的事务事件与稳定UUID实现。`GET /api/v1/cases/{case_id}/workflow-events?after=0&limit=100`按case序号升序返回事件、`next_after`、本次查询的`watermark`、`has_more`和`blocked`。分页只读取已提交SQL事件，不依赖outbox是否已投递、索引是否成功或连接落在哪个API进程。旧`/events`文件时间线的offset语义保持不变。

序号为算例内游标，不能混用其他算例的值。负数、超过JavaScript精确整数范围、非法页大小被拒绝；游标超过当前算例水位返回409 `event_cursor_ahead`，客户端重新读取当前状态并从零补拉。当前未裁剪持久事件；未来若加入保留期必须提供显式失效/快照协议，不能静默跳过历史。事件UUID在重投、断线和API重启后保持一致。序号允许合法间隔，不把中间空号猜成漏事件。

成功事件仍遵守既有完成可见性：若对应attempt的兼容产物尚未settled，查询停在该事件之前，返回`blocked=true`，游标不跨过它。之后再次查询同一游标即可继续。事件仅用于触发对账，页面读取Job/算例API的当前状态，不把旧成功通知作为当前完成证据。

`/ws/events?case_id=...&after=...`支持持久补拉并持续查询数据库。未提供after的旧连接从当前水位开始。原ready帧和文件快照通知保留。持久消息按序发送，跨API提交也能到达当前连接。进程内队列转发所选算例的临时通知，并为同一账户转发 `quota.warning` 和 `runtime.degraded`。持久消息不重复走本地队列。每轮数据库读取和临时通知发送前重新检查用户和算例访问权，关闭连接时回收三个监听任务。越界游标发送`cursor.reset`后关闭，HTTP接口也可独立完成补拉。[事件类型验收](FF-H16-event-topics-acceptance.md)

浏览器`caseEventStream.ts`将WebSocket视为刷新提示，真正游标只能由HTTP有序页推进。重连使用最近已处理游标，失败保留游标；刷新当前文件树与算例成功后才确认该页。重复/乱序/伪造的迟到成功提示不会直接设置Job结果。五秒补拉兜底不依赖WebSocket，重连后额外刷新当前状态以覆盖非持久文件通知；组件卸载后停止订阅，旧case消息不能刷新新case。JobsPanel继续读取数据库状态并保留原轮询，增加对账通知刷新和请求代数检查，迟到HTTP响应不能覆盖新响应。

验收包含SQLite/PostgreSQL各10项真实HTTP/WS检查：分页与稳定ID、事务回滚、非法/未来游标、完成可见性阻塞、跨API提交、同用户跨case隔离、断线补拉、socket游标重置、API退出/重启、跨用户/匿名拒绝。真实浏览器验证离线失败后Job面板恢复、重复/乱序成功提示不覆盖DB、socket重连和刷新不新增作业。前端生产构建、旧文件事件与JSONL时间线、真实outbox进程死亡重投兼容记录统一收于`tmp/mainline-N6-event-replay-evidence/`。

此项不代替N6-02的全部文件/索引对账，不关闭N6-03完整工作流恢复API、N6-04流程步骤视图、N6-05阶段与失效整合或N6-06日志游标/选中尝试/报告版本恢复。主线与295项全功能原始范围均保留。


## V18 进程退出后的重复投递

2026-11-18，在独立 PostgreSQL 数据库上分别运行文件存储和 SeaweedFS。先通过 DeepSeek 工具读取随机文件，完成一个真实 Windows 作业。写入另一份文件后，确认已提交的事件尚未被领取，终止 API 进程。重启后第一次投递完成全文索引事务和本地发布，在确认前再次终止进程。再次启动服务并等待生产租约自然过期，同一事件最终收到确认，领取次数为 2。作业、尝试、日志摘要、会话、事件顺序、索引构建标识、唯一命中和消费收据均符合预期。

修复前，在 S3 上首次发布后的重复投递多写了一组容量记录，占用 342 字节。现在投递器先读取持久索引收据并校验原始事件摘要。若另一个投递器在本次等待 S3 额度期间完成了消费，取得额度后再检查一次。首次处理仍在原写事务内提交索引和收据。旧索引缺少收据表时可以继续走正常处理，复用同一事件 ID 但更改载荷会报错。
