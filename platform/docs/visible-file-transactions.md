# 场景、几何、网格与消息图片的文件事务

2026-11-06。[旧写入口覆盖表](legacy-file-write-coverage.md) 中最后五类直接工作区写入已接入既有文件事务协议。

| 入口 | 新行为 | 保留的原规则 |
| --- | --- | --- |
| CAD 场景 WebSocket | `scene.json` 先记文件日志，再同事务保存变更事件；提交和收尾后才广播 | 每次消息重新核验账户/算例权限，revision/哈希冲突、对象校验、广播超时 |
| STEP 修复 | 修复 STEP 和 validation JSON 作为同一多文件事务 | 真实 CadQuery 转换、输入大小限制、来源摘要、显式覆盖规则 |
| Gmsh 预览 | 来源摘要对应的 VTU 通过文件事务保存 | 真实 meshio/VTK 转换、点/单元/输入容量限制 |
| 旧网格质量评估 | 保留原评估结果构造，在算例锁内事务保存 `quality.json` | 日志/输入指纹、最新质量政策、原工程阶段门禁 |
| 会话消息图片 | 一条消息的全部图片和消息事件使用同一次 SQL 提交证明 | 整批图片校验、最多三张/每张4 MiB、授权、会话空闲及 LLM/存储配额前置检查 |

消息图片不再靠异常处理循环删除新文件：一旦开始写入，由日志与 SQL 证明决定保留或回滚。提交确认丢失不能触发误删已提交消息的图片。没有图片的文本消息保持原有路径，不为其创建空文件事务。

## 验证

`visible_file_transactions_smoke.py` 使用真实 HTTP 和场景 WebSocket，实际终止 API，在新进程恢复。五个入口各覆盖首文件应用后、SQL commit 前、SQL commit 后三个窗口；文件系统/S3 与 SQLite/PostgreSQL 四组合共 60 组。

恢复检查不只看状态码：未提交内容必须等于原字节，已提交 STEP/验证摘要相符、VTU 可解析、质量报告绑定原日志、场景匹配已提交操作、两张图片完整对应唯一用户消息。再次协调读取不改写已保留文件。图片测试只替换模型响应流，不调用外部模型；文件保存、授权、消息数据库和恢复使用产品代码。

另运行原双 API 写入并发回归（SQLite/PostgreSQL 各 93 项），以及原 CAD 场景、真实几何修复、图片消息、网格质量门禁四套。附件故障钩子已移到实际事务应用点；异常后的断言改为先确认持久日志存在，再通过正式协调读取恢复，继续验证消息回滚和业务文件完整性。

第一轮兼容命令误用 `all` profile，没有启动隔离 API，四套均连接拒绝；未成功连接开发服务，不能计为产品失败或验收通过。随后 `writes` 选集又因不包含 `mesh_quality_smoke` 在执行前被拒绝。最终使用 `writes` 的三套和 `core` 的网格套件分别在隔离 API 中运行。原失败日志保留，不以重跑覆盖。

规范结果和实际终态以 `tmp/mainline-N2-visible-writers-evidence/` 为准。没有迁移开发库或重载端口8000。当前改动不把持锁转换改成无锁执行；长 I/O、取消/资源预算仍由 N4 原任务继续。

## 与 N2-06 验收的关系

本批补齐的是已确认直接写入缺口；其余普通文件、字典、上传、创建、输入封存、不可变产物和别名、旧 S3 staging 回传沿用各自已验证的恢复协议。核对 25 个注册处理器及 20 个存储/恢复核心文件与已有验收版本一致，因此使用清楚标明的增量证据，不声称所有历史专业流程在最终源码重新跑过完整部署矩阵。

源码扫描发现终端还有一处直接 `_fs_put`，已核对它只写本地 `.staging` 下的 cleanup-only 标记，不写算例用户版本；不能为了让搜索结果为零而删除该恢复证据。命名调用扫描仅辅助实际调用链审查，不等于对动态调用或任意用户原生命令的形式证明。

完整 finalizing 补交/缓存重建、人工选择与界面、索引对账、对象版本回收、跨主机部署及原 UDF409 的要求继续保留在 [原任务责任表](N2-06-acceptance-audit.md)。N2-06 是否关闭以主线台账及[原条件验收记录](mainline-acceptance-review.md)为准，不由本文中的测试数量单独决定。
